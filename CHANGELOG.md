Found internally from backlog item 129.
  - `stacks/30-hosts/persephone` gives the first-boot accounts fixed IDs outside the range the image assigns: `ec2-user` is 1000:1000, and `login_account_uid` and `login_account_gid` must be from 500 to 999. An `ec2-user` that exists with other IDs is now a logged failure, and its home is handed to it when another ID owns it. Found internally from backlog item 129.

  - `user_data.sh`, rendered with `templatefile()`, runs once at the first boot: it installs `python3` and `sudo` with a sudo rule for `ec2-user`, keeps the image's `zroot/home` from mounting over `/home`, mounts the two data volumes by their partition labels without ever formatting them, and creates the personal login account with its user ID (UID). Every step checks before it acts, and the script logs to `/var/log/user_data.log`.
  - The login account's primary group takes its own group ID (GID) from a new sensitive variable, `login_account_gid`, supplied by `op.env` and, for the Plan workflow, by the repository secret `TF_VAR_LOGIN_ACCOUNT_GID`, instead of reusing the user ID. Found internally from backlog item 129.
  - `user_data.sh` creates `ec2-user` with the user and group IDs that own `/home/ec2-user` on the home volume, because the image would otherwise give it the first free UID and `sshd` refuses a home owned by another user; an existing `ec2-user` with other IDs is given the home instead. Found internally from backlog item 129.
  - The login account's name and UID come from `op.env` and, for the Plan workflow, from two new repository secrets, so the public repository holds neither.
  - `ignore_changes` keeps the image and the user data and drops `instance_type`, decided 2026-10-08, so both serve the first boot only and the instance is replaced only by an explicit `-replace`. The stack README describes the user data and the rebuild in short. Found internally from backlog item 129.
  - `stacks/30-hosts/persephone` sizes the rebuilt host as a `t3a.medium` (two processors, 4 GiB of memory), the size of the current host, not a `t3a.small`, decided 2026-10-08. The name server process alone held about 1 GiB of resident memory on the current host, so a `t3a.small`'s 2 GiB could not also hold the 512 mebibyte (MiB) cap on the ZFS read cache, and processor use stayed far below the limit at any size. Found internally from backlog item 129.
